# Orchestrator

`internal/orchestration` owns the complete Orchestrator product: workspace coordination, conversation APIs, instructions, memory and managed work. It has no dependency on `internal/office`. Core run dispatch, runtime authentication and execution profiles are shared infrastructure. `workspace_orchestrators` registers core persona profiles; `orchestration_roles` stores behavioral templates. Registered orchestrators use ordinary task execution profiles, with `DirectProfile` resolved server-side. Do not apply legacy Office task profile pins to `orchestration_managed` tasks. Gate all Orchestrator capabilities together with `features.orchestration`; there is no separate Personal Assistant rollout switch. See `docs/decisions/2026-09-18-orchestrator-product-boundary.md` and the workspace-orchestrators spec/tests.

Core Automations may deliver to a workspace orchestrator through the injected `automation.OrchestratorTarget` interface. Start trigger producers only after the Orchestration queue is ready. A `dispatched` automation run confirms prompt delivery, not completion of requested work. Store its chat reference in `conversation_task_id`, never `task_id`: automation cleanup owns generated tasks but must not delete shared conversations.

A coordinator conversation runs only through its claimed run: the executor dispatch guard admits a native launch, resume, prompt, steer or model switch of a conversation task only for the broker-pinned session of the claimed run at the current intent revision. Every other task dispatches without that guard; legacy `orchestration_*` task metadata carries no dispatch authority.
