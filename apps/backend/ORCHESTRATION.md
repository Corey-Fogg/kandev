# Orchestration

`internal/orchestration` owns workspace coordinators: global roles, workspace assignments, persistent conversations, the coordinator runtime and the broker API. It has no dependency on `internal/office`. Core run dispatch, runtime authentication, execution profiles and task services are shared infrastructure. `workspace_orchestrators` registers core persona profiles; `orchestration_roles` stores behavioral templates. Registered coordinators delegate to ordinary task execution profiles, with `DirectProfile` resolved server-side. Do not apply legacy Office task profile pins to `orchestration_managed` tasks. `features.orchestration` gates everything here. Specs live in `docs/specs/orchestration/`; see ADRs `2026-09-07-workspace-orchestration` and `2026-09-18-orchestrator-product-boundary`.

Every coordinator conversation runs one path: the `orchestrator-broker-v1` MCP surface, a runtime JWT with the `workspace_coordinator` audience, and the `kandev_orchestrator` broker serving `models.WorkspaceBrokerTools()`. Add a broker operation by adding it to that catalog and a `/runtime/*` handler that authorizes from the token claims, requires the claimed run and session, and checks that every referenced task, workflow, repository or conversation belongs to `claims.WorkspaceID`. Never take scope from the request body. The broker has no shell, and the coordinator must not be able to select a bypass permission mode or create persistent permission rules. Only providers whose built-in tools are switched off or absent (`mcpprofile.BrokerCapableAgent`: claude-acp and mock-agent) may run a coordinator; configuration rejects other profiles and agentctl refuses to start one. Resumed and steered sessions must keep the broker policy recorded in session metadata.

Conversations are workspace-scoped: authorize every read and write by the conversation's workspace. The legacy `owner_user_id` column and any tables left by earlier development builds are never read. Schema changes are idempotent and replayable; add columns at the end and do not drop tables in the same change.

A coordinator conversation runs only through its claimed run: the executor dispatch guard admits a native launch, resume, prompt, steer or model switch of a conversation task only for the broker-pinned session of the claimed run at the current intent revision. Every other task dispatches without that guard; legacy `orchestration_*` task metadata carries no dispatch authority.

A delegated task (`orchestration_chief_id`) wakes its coordinator on a reportable state change or when one of its sessions starts waiting on a permission or question. The callback payload is a digest (state, latest session, reply excerpt, error, pending input); its idempotency key hashes that digest, so an unchanged update is never queued twice. An `agent.stalled` or `task.stalled` event on a delegated task wakes the coordinator once per stall episode with `stall_outcome` `no_progress`, `never_started` or `orphaned`. Digests and `workspace_tasks` rows carry the task's source issue (read only from the `jira_issue_*`/`linear_issue_*` metadata the issue watches write) and its most relevant pull request. `create_task` with `source` writes that metadata and the external id `<tracker>:<KEY>`, and returns the workspace's existing task for the issue with `duplicate: true` instead of creating another. `update_source_issue` comments on or moves only the issue recorded on the task, never one named by the caller. The `metrics` broker tool reports the coordinator's own delegated outcomes over 7 or 30 days (completion and failure counts, merged pull requests, cycle time, and priced cost including its conversation, with a count of unpriced usage events). A launching coordinator turn absorbs the coordinator's other queued callback runs into its own payload, and a user-message turn overtaken by a newer message finishes as `superseded` without starting an agent. A workspace has one orchestrator: `RegisterOrchestrator` refuses a second (`ErrOrchestratorExists`, 409 `orchestrator_exists`), legacy duplicates keep working, and the unique index appears once they are gone. An assignment's `display_name` is its instance name, separate from the role; the effective name (`display_name` or the role name) is what `GetAgentInstance`, the DTO `name`, the profile name and the conversation title carry, and a role save never overwrites it. Its settings `ask_before_create`, `auto_comment_source` and `auto_move_source_done` are stated in every prompt. With `ask_before_create`, `create_task` stores an `orchestration_task_proposals` row and a conversation comment whose ID is the proposal ID (`source: proposal`); approval creates the task once through a claimed row and a deterministic external ID, and every decision wakes the coordinator with a `proposal_decision` turn. Acceptance criteria live in `orchestration_goal` task metadata and the latest stall episode in `orchestration_stall`; the runtime writes only those two keys, through `TaskMetadataWriter`. `task_status done` is refused until every criterion is met, and only the delegating coordinator can `set_criteria`/`verify_criteria`. A delegated task with a source issue is commented on automatically when it enters REVIEW or COMPLETED (and moved to done when enabled); `orchestration_source_writebacks` claims each transition before posting, so a write happens at most once, and a failure wakes the coordinator once. Human metrics and proposal routes live under `/workspaces/:wsId/orchestrators/:id/…` and are served by the runtime through `orchestration.RuntimeFacade`; reading metrics never creates the conversation. Coordinator memory is workspace-scoped to the coordinator profile, written only through the `remember`/`forget` broker tools and injected into every prompt within a byte budget.

Every coordinator turn opens with the embedded `instructions/AGENTS.md`, never a stored per-persona copy, followed by the role instructions, a bounded workspace directory (workflows, steps, repositories, execution profiles), memory, recent messages and task updates. Broker tools publish typed schemas from `models.WorkspaceBrokerTools`; batched `manage_task`/`task_status` calls fan out in agentctl to the single-task endpoint, so every change is authorized on its own. A turn claimed for five minutes without binding a session is failed by the run dispatcher (`FailUnboundRuns`); a failed launch or agent failure posts one `runtime` note in the conversation, and retry accepts the run id.

Core Automations may deliver to a workspace coordinator through the injected `automation.OrchestratorTarget` interface. Start trigger producers only after the Orchestration queue is ready. A `dispatched` automation run confirms prompt delivery, not completion of requested work. Store its chat reference in `conversation_task_id`, never `task_id`: automation cleanup owns generated tasks but must not delete shared conversations.
