# Orchestrator

`internal/orchestration` owns the complete Orchestrator product: workspace coordination, conversation APIs, instructions, memory and managed work. It has no dependency on `internal/office`. Core run dispatch, runtime authentication and execution profiles are shared infrastructure. `workspace_orchestrators` registers core persona profiles; `orchestration_roles` stores behavioral templates. Registered orchestrators use ordinary task execution profiles. Do not apply legacy Office task profile pins to `orchestration_managed` tasks. Gate all Orchestrator capabilities together with `features.orchestration`; there is no separate Personal Assistant rollout switch. See `docs/decisions/2026-09-18-orchestrator-product-boundary.md` and the workspace-orchestrators spec/tests.

Core Automations may deliver to a workspace orchestrator through the injected `automation.OrchestratorTarget` interface. Start trigger producers only after the Orchestration queue is ready. A `dispatched` automation run confirms prompt delivery, not completion of requested work. Store its chat reference in `conversation_task_id`, never `task_id`: automation cleanup owns generated tasks but must not delete shared conversations.

A coordinator conversation runs only through its claimed run: the executor dispatch guard admits a native launch, resume, prompt, steer or model switch of a conversation task only for the broker-pinned session of the claimed run at the current intent revision. Every other task dispatches without that guard; legacy `orchestration_*` task metadata carries no dispatch authority.

A delegated task (`orchestration_chief_id`) wakes its coordinator on a reportable state change or when one of its sessions starts waiting on a permission or question. The callback payload is a digest (state, latest session, reply excerpt, error, pending input); its idempotency key hashes that digest, so an unchanged update is never queued twice. An `agent.stalled` or `task.stalled` event on a delegated task wakes the coordinator once per stall episode with `stall_outcome` `no_progress`, `never_started` or `orphaned`. Digests and `workspace_tasks` rows carry the task's source issue (read only from the `jira_issue_*`/`linear_issue_*` metadata the issue watches write) and its most relevant pull request. `create_task` with `source` writes that metadata and the external id `<tracker>:<KEY>`, and returns the workspace's existing task for the issue with `duplicate: true` instead of creating another. `update_source_issue` comments on or moves only the issue recorded on the task, never one named by the caller. A launching coordinator turn absorbs the coordinator's other queued callback runs into its own payload, and a user-message turn overtaken by a newer message finishes as `superseded` without starting an agent. Coordinator memory is workspace-scoped to the coordinator profile, written only through the `remember`/`forget` broker tools and injected into every prompt within a byte budget.

Every coordinator turn opens with the embedded `instructions/AGENTS.md`, never a stored per-persona copy, followed by the role instructions, a bounded workspace directory (workflows, steps, repositories, execution profiles), memory, recent messages and task updates. Broker tools publish typed schemas from `models.WorkspaceBrokerTools`; batched `manage_task`/`task_status` calls fan out in agentctl to the single-task endpoint, so every change is authorized on its own. A turn claimed for five minutes without binding a session is failed by the run dispatcher (`FailUnboundRuns`); a failed launch or agent failure posts one `runtime` note in the conversation, and retry accepts the run id.
